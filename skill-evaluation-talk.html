# Testing Kedro Nodes and Pipelines

Applies to Kedro 1.x. Kedro ships **no pytest plugin and no fixtures**. Every
fixture you use (`catalog`, `session`, sample data) must be defined in your own
test module or `conftest.py`.

## Pick the right kind of test

| What you are checking | Test type | Needs Kedro objects? |
|---|---|---|
| A node's logic | Unit test: call the function | No |
| Nodes wired together (names, `params:`, outputs) | Pipeline test: `DataCatalog` + `SequentialRunner` | Yes, in memory |
| The project boots and runs end to end | Smoke test: `KedroSession` | Yes, real config and data |

Prefer the first two. Never start a `KedroSession` to test a single node.

## Unit-testing a node

A node is a plain Python function. Call it directly.

```python
import pandas as pd
from spaceflights.pipelines.data_science.nodes import split_data


def test_split_data_returns_expected_sizes():
    data = pd.DataFrame(
        {"engines": [1, 2, 3, 4, 5], "crew": [4, 5, 6, 7, 8], "price": [1, 2, 3, 4, 5]}
    )
    params = {"test_size": 0.2, "random_state": 3, "features": ["engines", "crew"]}

    X_train, X_test, y_train, y_test = split_data(data, params)

    assert len(X_train) == 4
    assert len(X_test) == 1
```

Pass parameters as the plain dict the node receives. There is no `params:` here.

## Testing a pipeline in memory

Build a `DataCatalog` of `MemoryDataset`s and run with `SequentialRunner`.

```python
from kedro.io import DataCatalog, MemoryDataset
from kedro.runner import SequentialRunner
from spaceflights.pipelines.data_science import create_pipeline


def test_data_science_pipeline(model_input_table, model_options):
    catalog = DataCatalog(
        {
            "model_input_table": MemoryDataset(model_input_table),
            "params:model_options": MemoryDataset(model_options),
        }
    )

    result = SequentialRunner().run(create_pipeline(), catalog)

    metrics = result["metrics"].load()  # result values are datasets
    assert set(metrics) == {"r2_score", "mae", "max_error"}
```

`catalog["model_input_table"] = df` is equivalent: raw data is wrapped in a
`MemoryDataset` for you.

### The runner returns datasets, not data

In Kedro 1.x, `runner.run(...)` returns `{output_name: dataset}` for the
pipeline's outputs. Call `.load()` on the value, or use `catalog.load(name)`.

```python
# WRONG: compares a MemoryDataset with a dict, always fails
assert result["metrics"]["r2_score"] > 0

# Correct
assert result["metrics"].load()["r2_score"] > 0
```

### Provide every free input, including `params:`

The runner raises `ValueError: Pipeline input(s) {...} not found in the
DataCatalog` for any free input not in the catalog. Use `pipeline.inputs()` to
list them. Register parameters under their **literal** input name:

```python
# Correct
catalog["params:model_options"] = {"test_size": 0.2, ...}

# WRONG: the node asks for "params:model_options", so this is a missing input
catalog["model_options"] = {"test_size": 0.2, ...}
```

Outputs and intermediates do not need registering. The runner creates
`MemoryDataset`s for them. It also **releases** intermediates once their last
consumer has run, so `catalog.load("X_train")` after the run raises
`DatasetError`. Only free inputs and pipeline outputs survive. To assert on an
intermediate, slice so that it becomes an output (next section).

### Testing part of a pipeline

Slice the pipeline, then provide the free inputs of **the slice**:

```python
pipeline = create_pipeline().from_nodes("train_model_node").to_nodes("evaluate_model_node")
# pipeline.inputs() == {"X_train", "y_train", "X_test", "y_test"}

# Make an intermediate inspectable by ending the slice there
result = SequentialRunner().run(create_pipeline().to_outputs("X_train"), catalog)
X_train = result["X_train"].load()
```

Available: `only_nodes`, `from_nodes`, `to_nodes`, `from_inputs`, `to_outputs`,
`only_nodes_with_tags`, `filter`.

## Smoke-testing the whole project

```python
from pathlib import Path

from kedro.framework.session import KedroSession
from kedro.framework.startup import bootstrap_project

PROJECT_PATH = Path(__file__).resolve().parents[1]  # project root, not cwd


def test_project_runs():
    bootstrap_project(PROJECT_PATH)  # required, before KedroSession.create
    with KedroSession.create(project_path=PROJECT_PATH) as session:
        session.run(pipeline_names=["data_processing"])
```

- Without `bootstrap_project`, `create` fails with `ValueError: Package name not
  found`.
- This uses the real `conf/base/catalog.yml` and **writes real files** to
  `data/`. Keep these tests few, and point the catalog elsewhere through a test
  env if that matters.
- One session = one run. A second `session.run()` raises `KedroSessionError`.
- `pipeline_name=` is deprecated. Use `pipeline_names=[...]`.

### Test environments and runtime parameters

```python
KedroSession.create(
    project_path=PROJECT_PATH,
    env="test",                                          # conf/test/
    runtime_params={"model_options": {"test_size": 0.5}},  # nested dict
)
```

- `runtime_params` must be **nested**. A dotted key like
  `{"model_options.test_size": 0.5}` is not expanded. It becomes a literal key and
  the real value is unchanged. (Only the CLI `--params` parses dots.)
- A misspelled or missing `env` is **not** an error. Kedro silently uses base only.
- A `parameters.yml` in the test env **replaces** whole top-level keys from
  `base`. Repeat every sibling key you still need.

## Wrong APIs: do not generate these

```python
# WRONG: none of these exist in Kedro 1.x
context.run()                                      # KedroContext has no run()
from kedro.framework.context import load_context
from kedro.runner import KedroSession              # it's kedro.framework.session
from kedro.io import KedroDataCatalog              # it's kedro.io.DataCatalog
def test_x(kedro_session, catalog): ...            # no built-in fixtures
```

## Fixtures and layout

Write fixtures yourself, in `conftest.py` to share them:

```python
# tests/conftest.py
import pandas as pd
import pytest


@pytest.fixture
def model_input_table():
    return pd.DataFrame({"engines": [1, 2, 3, 4, 5], "crew": [4, 5, 6, 7, 8],
                         "passenger_capacity": [5, 6, 7, 8, 9],
                         "price": [120, 290, 30, 40, 50]})


@pytest.fixture
def model_options():
    return {"test_size": 0.2, "random_state": 3,
            "features": ["engines", "passenger_capacity", "crew"]}
```

`tests/` sits at the project root and mirrors `src/<package>/`:

```
src/<package>/pipelines/data_science/nodes.py
tests/pipelines/data_science/test_nodes.py
tests/pipelines/data_science/test_pipeline.py
tests/test_run.py
```

Install the project (`pip install -e .`) so tests can import it, and run
`pytest` from the project root. Coverage comes from `pytest-cov` through
`[tool.pytest.ini_options] addopts = "--cov src/<package>"` in `pyproject.toml`.

# Writing tests for a Kedro project

Kedro tests are ordinary pytest tests. What makes them Kedro-specific is a
small set of runtime behaviours that look reasonable to guess and are easy to
guess wrong. This skill covers those. Everything else is plain pytest.

Kedro ships no pytest plugin, so there are no `kedro_session`, `kedro_context`
or `catalog` fixtures. If a test needs one, define it in the test module or in
`tests/conftest.py`. A test that asks for a fixture nobody defined fails at
collection.

## Choose the smallest test that answers the question

Each layer up costs more and fails for more reasons, so test at the lowest
layer that can catch the bug:

1. **Node logic** → call the node function directly. Nodes are plain Python
   functions, so a unit test needs no catalog, runner or session.
2. **Wiring** (dataset names, `params:` inputs, which outputs exist) → run the
   pipeline in memory with `DataCatalog` + `SequentialRunner`.
3. **The project boots end to end** → `KedroSession` smoke test. It reads the
   real `conf/` and writes real files to `data/`, so keep it to one or two
   tests.

## 1. Node unit tests

```python
import pandas as pd
from my_project.pipelines.data_science.nodes import split_data


def test_split_data_holds_out_test_fraction():
    data = pd.DataFrame({"engines": [1, 2, 3, 4, 5], "price": [1, 2, 3, 4, 5]})
    params = {"test_size": 0.2, "random_state": 3, "features": ["engines"]}

    X_train, X_test, y_train, y_test = split_data(data, params)

    assert (len(X_train), len(X_test)) == (4, 1)
```

The node receives parameters as a plain dict, so pass a dict. The `params:`
prefix only exists in pipeline wiring.

## 2. In-memory pipeline tests

```python
from kedro.io import DataCatalog, MemoryDataset
from kedro.runner import SequentialRunner
from my_project.pipelines.data_science import create_pipeline


def test_data_science_pipeline_produces_metrics(model_input_table, model_options):
    catalog = DataCatalog(
        {
            "model_input_table": MemoryDataset(model_input_table),
            "params:model_options": MemoryDataset(model_options),
        }
    )

    result = SequentialRunner().run(create_pipeline(), catalog)

    metrics = result["metrics"].load()
    assert set(metrics) == {"r2_score", "mae", "max_error"}
```

`catalog["model_input_table"] = df` also works. Raw data is wrapped in a
`MemoryDataset` for you.

Four behaviours shape these tests:

**The runner returns datasets, not data.** `runner.run()` returns
`{output_name: dataset}` for the pipeline's outputs. Call `.load()` on each
value (or use `catalog.load(name)`). Pre-1.0 runners returned the data itself,
so older examples index straight into the result, as in
`result["metrics"]["r2_score"]`. On 1.x that fails because the value is a
`MemoryDataset`.

**Every free input must be in the catalog.** Otherwise the run stops with
`ValueError: Pipeline input(s) {...} not found in the DataCatalog`.
`pipeline.inputs()` tells you exactly what to provide.

**Parameters are registered under their literal input name.** If a node
declares `"params:model_options"`, the catalog key is `"params:model_options"`.
Registering `"model_options"` leaves the input missing.

**Intermediates are released after use.** The runner creates `MemoryDataset`s
for intermediate outputs, then releases each one once its last consumer has
run. So `catalog.load("X_train")` after the run raises `DatasetError: ... has
not been saved yet`. Only free inputs and pipeline outputs survive. To check
an intermediate, end the pipeline there so it becomes an output:

```python
result = SequentialRunner().run(create_pipeline().to_outputs("X_train"), catalog)
X_train = result["X_train"].load()
```

### Running part of a pipeline

`only_nodes`, `from_nodes`, `to_nodes`, `from_inputs`, `to_outputs`,
`only_nodes_with_tags` and `filter` return a new `Pipeline`. The catalog must
satisfy the **slice's** `.inputs()`, not the full pipeline's:

```python
sliced = create_pipeline().from_nodes("train_model_node").to_nodes("evaluate_model_node")
assert sliced.inputs() == {"X_train", "y_train", "X_test", "y_test"}
```

`MemoryDataset` copies pandas DataFrames and numpy arrays on load and save, so
a node that mutates its input cannot corrupt the fixture between tests.

## 3. KedroSession smoke tests

```python
from pathlib import Path

from kedro.framework.session import KedroSession
from kedro.framework.startup import bootstrap_project

PROJECT_PATH = Path(__file__).resolve().parents[1]


def test_data_processing_runs():
    bootstrap_project(PROJECT_PATH)
    with KedroSession.create(project_path=PROJECT_PATH) as session:
        session.run(pipeline_names=["data_processing"])
```

Why each line looks like this:

- `bootstrap_project` reads `pyproject.toml` and registers the project's
  package and settings. Without it, `KedroSession.create` fails with
  `ValueError: Package name not found`.
- Resolve the project root from `__file__`. The starter template uses
  `Path.cwd()`, which only works when pytest runs from the project root.
- Use `pipeline_names=[...]`. `pipeline_name=` is deprecated.
- A session runs once. A second `session.run()` raises `KedroSessionError`, so
  create a new session per run.
- `session.run()` also returns `{name: dataset}`, same as the runner.

### Test environments and runtime parameters

```python
KedroSession.create(
    project_path=PROJECT_PATH,
    env="test",
    runtime_params={"model_options": {"test_size": 0.5}},
)
```

Three traps:

- **`runtime_params` must be nested.** Through the Python API, a dotted key
  like `{"model_options.test_size": 0.5}` is stored as a literal key and the real
  value is unchanged. Only the CLI's `--params` splits on dots.
- **A missing env is silent.** `env="tset"` raises nothing and you get base
  config, so a typo turns a test-config test into a production-config test.
- **An env's parameters file replaces whole top-level keys.** If
  `conf/test/parameters.yml` sets only `model_options.test_size`, the other
  `model_options` keys from `base` are gone. Repeat the keys you need.

## Imports and APIs that do not exist in Kedro 1.x

Models trained on older Kedro code tend to produce these:

| Don't write | Write |
|---|---|
| `context.run()` / `KedroContext.run` | `KedroSession.create(...).run()` |

| `from kedro.runner import KedroSession`, `from kedro.io import KedroSession` | `from kedro.framework.session import KedroSession` |
| `from kedro.io import KedroDataCatalog` | `from kedro.io import DataCatalog` |
| `def test_x(kedro_session, catalog):` with no fixture defined | Define the fixtures in `conftest.py` |

Lessons

What we would do again

The main lesson is that a skill is only as good as the rules under it. Two of our wrong claims came from the shared fact sheet, and neither writing style caught them. Running the examples did.

Run every example in the skill, and check that its comments say what the test proves. The hand-written version had a comment saying that indexing a runner's result "always fails". The test had actually asserted a TypeError. Nobody noticed the mismatch until we read the two versions side by side.

compares a MemoryDataset with a dict, always fails
TypeError: 'MemoryDataset' object is not subscriptable

Test the behaviour a user relies on, not just that nothing crashed. A misspelled environment name passed our first test, because that test only checked that loading did not raise. The real failure came later, when the run started.

The eval loop mattered more than the writing. skill-creator's real value was the cycle of running with and without the skill, grading the results, and fixing what failed. Writing a skill by hand has no such step unless we add one. By round 3 most failures were in our tests rather than the skills, so a judge model should not decide anything a code check can.
